> 适用方向：A · Coding Agent Harness（首选方向）

> 使用方式：从上到下执行；每完成一项就在复选框中打勾，并把证据链接、commit hash、MR 编号或 CI 链接补到对应位置。

## 0. 一页总览：最终必须交出什么

### 0.1 项目本体

- [ ] 一个真实可运行、非玩具级的 Coding Agent Harness。
- [ ] Harness 内核由自己编码，不寄生于现成 Agent 框架的高层循环。
- [ ] 自己实现 Agent 主循环：组织上下文 → 调用 LLM → 解析动作 → 分发工具 → 回灌结果 → 判断停机。
- [ ] 提供可注入 mock/stub 的 LLM 抽象层。
- [ ] 六个维度都有可运行的最低实现：决策、工具、记忆、治理、反馈、配置。
- [ ] 从治理、反馈闭环、扩展/工具分发、记忆/上下文等机制密集维度中选一个作为主要贡献，并做到足够深入。
- [ ] 核心机制在移除真实 LLM 后仍能通过确定性单元测试验证。
- [ ] 至少三个职责清晰的功能模块。
- [ ] 提供可一键运行的测试命令。
- [ ] 提供用户可访问的 WebUI。
- [ ] 提供截止前可访问的线上部署 URL。
- [ ] 提供一种正式分发方式：容器、二进制或包管理器；可组合使用。

### 0.2 文档与过程证据

- [ ] `SPEC.md`
- [ ] `PLAN.md`
- [ ] `SPEC_PROCESS.md`
- [ ] `README.md`
- [ ] `AGENT_LOG.md`
- [ ] `REFLECTION.md`（1500–2500 字，必须由本人撰写；AI 只能辅助润色且要标注）
- [ ] 机制演示脚本或测试
- [ ] 完整、可审查的 commit 历史
- [ ] 多个 GitLab Merge Request（MR），不能一次提交全部代码
- [ ] `.gitlab-ci.yml`，且必须存在名为 `unit-test` 的 job
- [ ] 最后一次 GitLab CI/CD Pipeline 为 passed
- [ ] 分发产物或构建配置
- [ ] 安全凭据配置、查看状态、更新、清除流程
- [ ] 无任何真实 API Key、token 或其他凭据进入仓库、日志或 Git 历史

### 0.3 三条最高优先级硬门禁

- [ ] **Gate A：** `SPEC.md` 与 `PLAN.md` 完成并通过陌生智能体冷启动验证之前，不得编写实现代码。
- [ ] **Gate B：** 每个实现任务必须严格执行 TDD：先看到失败测试，再写最少实现使其通过，然后重构。
- [ ] **Gate C：** 不得用 LangChain `AgentExecutor`、AutoGen、CrewAI、LlamaIndex Agent 或编码智能体 SDK 的 Agent Runner 代替自己的 Harness 主循环。

## 2. 阶段二：通过 brainstorming 决定“到底做什么”

### 2.1 定义真实问题与目标用户

- [ ] 触发 Superpowers `brainstorming`。
- [ ] 用一句话描述 Harness 的真实用途，格式建议：
  - [ ] “为 ______ 用户，在 ______ 场景中，安全、可验证地完成 ______ 编码任务。”
- [ ] 明确目标用户是谁：个人开发者、学生、团队 reviewer、维护遗留项目的工程师或其他具体群体。
- [ ] 明确为什么用户会使用它，而不是直接使用 Codex/Claude Code/OpenCode。
- [ ] 明确 30 秒项目介绍，并记录在 `SPEC.md` 草稿和 `README.md` 草稿中。
- [ ] 列出至少三个真实使用场景。
- [ ] 列出明确的非目标，防止项目膨胀。

### 2.2 确定 Coding Agent 的任务边界

- [ ] 明确 Agent 可以读取哪些文件。
- [ ] 明确 Agent 可以修改哪些文件。
- [ ] 明确 Agent 可以执行哪些 shell 命令。
- [ ] 明确 Agent 如何运行构建、测试、lint 和类型检查。
- [ ] 明确 Agent 的最大循环步数、token/费用预算、命令超时和失败重试上限。
- [ ] 明确任务完成的客观判断，不允许只靠 LLM 自称完成。
- [ ] 明确何时必须停止并请求人工处理。
- [ ] 明确项目是否支持真实 LLM；无论是否支持，都必须先支持 mock LLM。

### 2.3 设计 A 方向强制的四类领域机制

#### 动作/工具

- [ ] 列出 Agent 能执行的每个工具。
- [ ] 为每个工具定义输入 schema、输出 schema、错误类型和超时行为。
- [ ] 至少覆盖读取文件、受限写文件、执行命令、运行测试中的合理子集。
- [ ] 明确工具调用是否有工作目录限制。
- [ ] 明确工具输出如何截断、摘要或保存，防止上下文污染。

#### 客观反馈信号

- [ ] 选择至少一种确定性校验器：测试、lint、类型检查、构建或自定义规则检查。
- [ ] 定义校验器如何解析结果。
- [ ] 定义失败如何分类，例如：语法错误、测试失败、超时、权限失败、环境失败。
- [ ] 定义反馈如何重新注入 Agent 上下文。
- [ ] 定义反馈循环的最大修复次数。
- [ ] 明确“通过”的客观证据。

#### 危险动作与治理

- [ ] 列出必须阻断的危险动作，如批量删除、覆盖系统目录、访问凭据、强推、部署、数据库破坏性操作。
- [ ] 列出必须人工审批的动作。
- [ ] 列出默认允许的低风险动作。
- [ ] 设计确定性的 `guardrail(action)` 或等价接口。
- [ ] 设计人工审批状态机：pending → approved/denied/expired。
- [ ] 设计中断后恢复机制，确保审批前工具绝不会执行。
- [ ] 设计审计记录，保存动作、原因、审批者、时间和结果。

#### 记忆

- [ ] 明确跨会话需要记住什么：项目约定、历史决策、失败方案、代码库知识或用户偏好。
- [ ] 明确哪些内容绝对不能进入记忆：API Key、密码、敏感源码片段或无价值噪声。
- [ ] 设计存储格式和位置。
- [ ] 设计检索方式，避免每次把全部记忆塞进上下文。
- [ ] 设计记忆写入、读取、更新、清除和去重规则。
- [ ] 设计 mock LLM 下可验证的记忆测试。

### 2.4 选择一个“主要贡献”维度

- [ ] 从以下方向选择一个主角：
  - [ ] 治理：命令解析、策略引擎、范围围栏、HITL 状态机、沙箱。
  - [ ] 反馈闭环：多类传感器、失败分类、自动修复循环、客观停机。
  - [ ] 扩展：工具注册与分发、插件机制、多 Agent 编排。
  - [ ] 记忆/上下文：自己实现存储、检索、压缩、选择和隔离。
- [ ] 说明为什么该维度是用户真实痛点，而不是为了凑要求。
- [ ] 为该维度列出至少三个深度特性。
- [ ] 为每个深度特性定义确定性测试。
- [ ] 明确其他五个维度的最低可运行范围，防止主角之外完全缺失。

### 2.5 技术与产品决策

- [ ] 选择语言与框架，并说明理由。
- [ ] 明确不会使用现成 Agent 高层循环代替自研内核。
- [ ] 若使用底层库，列出允许范围：HTTP、供应商单次补全 SDK、解析库、向量库等。
- [ ] 选择真实 LLM 供应商或声明初版仅提供适配接口。
- [ ] 选择 WebUI 技术栈。
- [ ] 若有前端，评估并记录所选 Open Design 设计系统与 Skill。
- [ ] 选择分发方式：优先考虑 Docker，或选择二进制/包管理器并说明原因。
- [ ] 选择部署方式，并确认能提供 WebUI 公网地址。
- [ ] 选择凭据安全存储方案。

### 2.6 brainstorming 签字

- [ ] 智能体分块展示设计。
- [ ] 本人逐块质询并修改模糊点。
- [ ] 在 `SPEC_PROCESS.md` 记录至少三轮关键迭代：AI 建议、本人判断、最终决策。
- [ ] 明确哪些 AI 建议被采纳、哪些被拒绝以及原因。
- [ ] 对最终设计明确签字确认。

### 阶段 Gate 2

- [ ] 项目问题、用户、边界、非目标均已明确。
- [ ] 四类领域机制均有设计。
- [ ] 六维 Harness 均有最低实现规划。
- [ ] 已选定且论证主要贡献维度。
- [ ] brainstorming 过程有真实记录。
- [ ] 当前仍未编写实现代码。

## 4. 阶段四：完成 `PLAN.md`

### 4.1 使用 `writing-plans`

- [ ] 在 SPEC 签字后触发 Superpowers `writing-plans`。
- [ ] 把实现拆成每步约 2–5 分钟的原子操作。
- [ ] 每个 task 能由一个新鲜 subagent 在一次会话内完成。
- [ ] 每个 task 有唯一编号。

### 4.2 每个 task 必须包含

- [ ] 目标。
- [ ] 前置依赖。
- [ ] 精确文件路径。
- [ ] 预期实现要点。
- [ ] 首先编写的失败测试。
- [ ] 预期的红色失败现象。
- [ ] 最小实现步骤。
- [ ] 重构点。
- [ ] 验证命令。
- [ ] 完成标准。
- [ ] 对应的 commit/MR 计划。

### 4.3 推荐 task 分组

- [ ] T01：项目骨架、构建和测试入口。
- [ ] T02：核心数据模型与错误模型。
- [ ] T03：可注入的 LLM 接口与 scriptable mock LLM。

## 5. 阶段五：陌生智能体冷启动验证 SPEC + PLAN

## 6. 阶段六：按 worktree + subagent + TDD 实现

### 6.1 每个 task 的标准执行模板

- [ ] 从最新默认分支建立独立 branch。
- [ ] 为该 branch 创建独立 git worktree。
- [ ] 在 `AGENT_LOG.md` 记录 task、branch、worktree 和 subagent。
- [ ] 给 subagent 只提供完成当前 task 所需的最小 context。
- [ ] 触发 `test-driven-development`。
- [ ] 先写一个会失败的测试。
- [ ] 运行测试并保存失败输出，确认失败原因正确。
- [ ] 写最少实现代码使测试通过。
- [ ] 再次运行测试并保存通过输出。
- [ ] 在测试保护下重构。
- [ ] 运行该 task 的全部验证命令。
- [ ] 先做 spec 合规审查。
- [ ] 再做代码质量审查。
- [ ] 修复所有 Critical 问题。
- [ ] 提交原子 commit。
- [ ] 在 commit message 或 MR 描述中写明由哪个 subagent 完成、本人修改了什么。
- [ ] 推送 branch 到 NJU GitLab。
- [ ] 创建 MR。
- [ ] 等 CI 通过并完成 review 后合并。
- [ ] 在 `PLAN.md` 勾选 task 并填写 commit hash。
- [ ] 在 `AGENT_LOG.md` 写总结。

### 6.2 TDD 证据纪律

- [ ] 每个核心功能都有“先红”的证据。
- [ ] 失败测试确实因缺少目标实现而失败，不是因语法错误或环境坏掉。
- [ ] 绿色阶段只写最少代码。
- [ ] 重构没有改变外部行为。
- [ ] 禁止先写实现再补测试。
- [ ] 禁止删除或弱化失败测试来让 CI 变绿。
- [ ] 测试文件纳入代码审查，视为 Agent 的不可删除护栏。

### 6.3 两阶段代码审查

#### 第一阶段：Spec 合规

- [ ] 是否实现了 task 要求的全部行为。
- [ ] 是否加入了未授权功能。
- [ ] 是否违反非目标或安全边界。
- [ ] 是否有与 SPEC 不一致的默认行为。
- [ ] 验收标准是否都有测试或证据。

#### 第二阶段：代码质量

- [ ] 模块职责是否单一。
- [ ] 接口和错误模型是否清晰。
- [ ] 是否存在重复、过度设计或隐藏耦合。
- [ ] 是否有安全问题。
- [ ] 是否有不可控副作用。
- [ ] 日志是否可能泄漏凭据。
- [ ] 测试是否稳定、可读、确定性强。
- [ ] 是否需要补充注释解释“为什么”，而不是重复“做什么”。

## 7. Harness 内核专项验收

### 7.1 自研主循环

- [ ] 主循环代码清楚展示 context 组织。
- [ ] 每一轮只通过 LLM 抽象获得下一动作。
- [ ] 动作解析失败有确定行为。
- [ ] 工具分发由自己的代码执行。
- [ ] 工具结果被转化为 observation 并回灌。
- [ ] 反馈传感器结果被回灌。
- [ ] 存在完成、最大步数、预算耗尽、人工中止、重复失败等停机条件。
- [ ] 主循环可完全使用 mock LLM 运行。
- [ ] 未调用任何现成框架的 Agent Runner。

### 7.2 LLM 抽象与 mock

- [ ] 接口只描述单次模型调用，不暗含高层 Agent 循环。
- [ ] mock 可以按脚本依次返回多个动作。
- [ ] mock 可以注入解析失败。
- [ ] mock 可以模拟工具失败后的修正动作。
- [ ] mock 测试不联网、不读取真实 key、结果可重复。

### 7.3 工具系统

- [ ] 工具注册、schema、查找和调用由自己实现。
- [ ] 未知工具被明确拒绝。
- [ ] 参数校验失败不会执行工具。
- [ ] 工作目录和文件范围受限。
- [ ] 命令有 allow/ask/deny 策略。
- [ ] 工具有超时和输出上限。
- [ ] 工具异常被结构化回灌，不导致 Harness 崩溃。

### 7.4 治理与 HITL

- [ ] 危险动作识别是代码机制，不是 prompt 提醒。
- [ ] 能确定性拦截至少一个危险命令。
- [ ] 审批前不执行工具。
- [ ] 拒绝审批后 Agent 得到结构化反馈。
- [ ] 批准后只执行原始已审批动作，防止参数被替换。
- [ ] 审批有超时、审计和恢复。
- [ ] 默认最小权限。

### 7.5 反馈闭环

- [ ] 传感器由代码运行和解析。
- [ ] 测试失败可以分类。
- [ ] 失败结果进入下一轮上下文。
- [ ] mock LLM 在收到失败后会给出不同的下一动作。
- [ ] 修复后再次运行传感器。
- [ ] 达到通过标准后停机。
- [ ] 连续失败超过阈值后升级给人。

### 7.6 记忆

- [ ] 记忆存储和检索由自己的代码实现；若作为重点维度，不得直接使用框架自带 memory。
- [ ] 支持写入、按需选择、更新和清除。
- [ ] 不全量注入上下文。
- [ ] 敏感数据被拒绝或脱敏。
- [ ] 重复和过期信息有处理策略。
- [ ] 跨会话行为有确定性测试。

### 7.7 配置

- [ ] 配置可声明模型、工具、权限、预算、反馈和记忆策略。
- [ ] 配置有 schema 校验。
- [ ] 错误配置快速失败并给出明确错误。
- [ ] 默认配置安全。
- [ ] 配置、规则、Skill 和 prompt 没有被当作 Harness 核心工作量。
